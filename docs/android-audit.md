# Android platform audit

One row per doc page read, what it requires, and whether we comply. Appended to,
never rewritten — a finding's history is the useful part.

Method and scope: `.claude/skills/android-docs/SKILL.md`. Enforcement:
`__tests__/platform.test.ts`.

**Scope is our surface, not the site.** Compose, Wear, TV, Auto, XR, games, ML
Kit, CameraX and Health do not apply to this app and reading them is waste.
Coverage means exhaustive over what we actually ship.

## Cashfree WebCheckout — package visibility, 2026-08-30

**Pages read:** [Cashfree Android WebCheckout](https://www.cashfree.com/docs/payments/online/mobile/android), [Android package visibility (API 30)](https://developer.android.com/training/package-visibility)

### Requirement

Android 11 (API 30+) restricts an app's ability to see other installed packages. Without explicit `<queries>` declarations, `PackageManager.queryIntentActivities()` returns an empty list and the Cashfree SDK cannot detect installed UPI apps (Google Pay, PhonePe, Paytm, BHIM). The WebCheckout approach also requires server-side order creation and server-side payment verification — the client callback (`onVerify`) must not be trusted to credit tokens alone.

| Area                  | Requirement                                                                                                      | Compliance                                                                                               |
| --------------------- | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Package visibility    | `<queries>` with UPI package names + `upi://` intent in `AndroidManifest.xml`                                    | **DONE** — added in `android/app/src/main/AndroidManifest.xml`; asserted in `platform.test.ts`           |
| Server-side order     | `paymentSessionId` must come from a server call with client-secret; never embed Cashfree secret in the RN bundle | **DONE** — `create-order` Edge Function holds secret via `Deno.env`; `billing.ts` has no secret          |
| Server-side verify    | Client `onVerify` callback must be confirmed S2S before crediting tokens                                         | **DONE** — `verify-order` Edge Function calls `GET /orders/{orderId}` before `credit_purchased_recharge` |
| Drop checkout         | Deprecated; use WebCheckout (`doWebPayment`)                                                                     | **DONE** — `billing.ts` uses `doWebPayment(cfSession)`                                                   |
| Sandbox vs production | `CFEnvironment.SANDBOX` in non-prod; production gated behind `PAYMENTS_ENABLED` (ADR-0022)                       | **DONE** — `CASHFREE_SANDBOX_CHECKOUT = APP_ENV !== 'production'`                                        |

### Missing `TextDecoder` broke call answer on API 29, 2026-09-05

The two-phone matrix could not complete a single connected call. The ledger was
the tell: `calls` reached `status = 'active'` with a `started_at`, so the answer
RPC succeeded, yet the caller sat on the outgoing screen until the 30s ring
timeout. The two devices disagreed, which pointed at the client rather than the
server.

Callee logcat on the API 29 Redmi ended signalling immediately after
`addTransceiver` with a repeated
`ReferenceError: Property 'TextDecoder' doesn't exist`. The API 36 Samsung never

supabase-js's PKCE capability gate tests for it — but not `TextDecoder`, which

callee therefore never produced an answer SDP.

### Video m-line carried no msid, 2026-09-05

With calls connecting, each phone showed its own camera and neither showed the
other's, while audio was fine. The asymmetry between the two media types is the
whole diagnosis: audio is attached with `pc.addTrack(track, stream)`, which
signals an `msid`, whereas the video transceiver was created with
`pc.addTransceiver('video', { direction: 'sendrecv' })` and no stream at all.

Without an `msid` on that m-line the peer's `track` event for video fires with an
empty `streams` array, so `if (e.streams[0])` discarded it and the remote stream
only ever held audio. `@livekit/react-native-webrtc` maps `init.streams` to
`streamIds`, so passing the local stream is enough; the track handler was left
alone deliberately, since making it tolerate a stream-less event would hide the
next occurrence of this rather than fix it.

Three harness corrections came out of the same investigation, all recorded
because they invalidated earlier runs rather than merely slowing them:

- The caller and callee flows ran in sequence, and Maestro's on-device driver
  startup alone exceeds the 30s ring window, so every "answer" arrived after the
  call had already become `unanswered`. They now start together.
- MIUI rejects Maestro's driver APK with `INSTALL_FAILED_USER_RESTRICTED`; that
  install is gated behind "USB debugging (Security settings)", which requires a
  Mi account. `uiautomator dump` and `input tap` are not gated, so the callee is
  driven with those directly. Dumping to `/dev/tty` is killed mid-write on that

- `uiautomator dump` returns "could not get idle state" for the whole ring
  window, because every waiting phase of CallScreen runs `CallingDots` forever
  and UI Automator waits for a quiescent window. The harness now zeroes the three
  animation scales, which is both what the UI Automator setup guidance asks for
  and the signal behind `useReducedMotion`, so those components render statically.

## 2026-09-05 — UI haptics, and the frosted bars verified on API 36

**Pages read.** `develop/ui/views/haptics/haptics-principles`, plus the SDK's own

than a reference page (the HTML reference did not render the API-level table to

**What they require.** A predefined action goes through
`View.performHapticFeedback` with a `HapticFeedbackConstants` value, not
`Vibrator`/`VibrationEffect`. That runs the OEM's tuned waveform, keeps the app
consistent with the system — the docs call the consistency an accessibility
consideration — and respects the user's touch-feedback setting.
`FLAG_IGNORE_GLOBAL_SETTING` is strongly discouraged.

**Where we were.** `src/lib/haptics.ts` called `Vibration.vibrate(ms)`. So every
send and every long-press buzzed a user who had switched haptics off in
Settings, and the durations were our guesses at waveforms the platform ships.

page discourages it, and `api-versions.xml` records it `deprecated=33` while this
app targets 36. `CONFIRM`/`REJECT` are `since=30` and are guarded, falling back

OTA-skew window where a JS bundle is newer than the APK. Asserted in
`platform.test.ts` with comments stripped first, since the file explains the
discouraged API and matching prose would fail correct code.

**Blur, closed out and measured.** The frosted bars rendered as solid black
slabs on the S22 and the Redmi. Cause was ours and had nothing to do with R8 or
Fabric: `Frost` converted the token colour to a SIGNED 32-bit ARGB int, and RN's
colour normaliser rejects negative numbers, so the prop was dropped and the view
kept its default. `normalizeColor(-1929379841)` returns null;
`normalizeColor('rgba(255,255,255,0.55)')` returns 4294967180. Passing the token
string and deleting the hand-rolled converter fixed it (39a4c0e). Two
alternatives were disproved rather than assumed: R8 does not strip the
`@ReactProp` setters (RN ships the keep rule, and `mapping.txt:183099` shows
`setTintColor` unrenamed in the shrunk build), and the logcat line "Could not
find generated setter for PappalBlurSurfaceManager" is a routine RN warning that
also appears for `RootViewManager` and `SafeAreaProviderManager`.

Verified on the S22 (API 36, internal build, versionCode 10055): the chat header
and composer render as light plates with readable content, and content passing
under the FloatingToolbar is visibly blurred — luminance standard deviation 20.92
just above the bar, 8.24 inside it, 0.0 below. Variance preserved but softened is
a blur; a flat plate would read 0.0 and a transparent bar would match the content.

`RenderEffect.createBlurEffect` is API 31, and `onDraw` gates on it, so below
that the native surface could only ever reach `drawSolidFallback`. The JS side
now checks `Platform.Version` and never mounts it there (13d12e4), which is why
the Redmi (API 29) correctly shows a plate rather than a blur.

## Frame measurement protocol, 2026-09-06

### Preconditions — without these the numbers are wrong

**Samsung S22 Ultra: set "Motion smoothness" to "Adaptive" before any
measurement.** The S22 ships with this option disabled by default. With it
disabled the display locks to 60Hz regardless of what `MainActivity`
requests, so `dumpsys gfxinfo` and `scripts/framestats.mjs` report a 16.7ms
vsync period and `inferredHz: 60.0` even while the app has voted for 120Hz.
Any frame-budget number taken without this setting is a 60Hz number on a
120Hz panel, and the 95%-within-budget gate, which targets 8.33ms, will fail
every frame. Path: Settings → Display → Motion smoothness → Adaptive.

**Redmi Note 7 Pro: runs the Metro-served DEBUG build only.** This is the
phone on the daily-driver bench. Its numbers are not release numbers. It runs
API 29, a 60Hz panel, and a Metro-served dev-mode React bundle — no R8, no
Baseline Profile, no bundle minification. The ~500ms chat tap→first-paint
measured here was investigated on 2026-09-03 and confirmed to be a debug
artefact (see the ChatScreen chat-open entry in the "Closed" table). Do not
cite any Redmi timing as a performance claim, only as an API-floor
compatibility check. The Macrobenchmark cannot run on it at all: the
benchmark APK cannot be installed over the debug APK without uninstalling, and
uninstalling clears the signed-in session.

### scripts/framestats.mjs — what it does

`scripts/framestats.mjs` is the automated gate for `adb shell dumpsys gfxinfo`
frame data. Read the file before running it rather than relying on this
summary; the header comment records decisions about the format.

Key behaviours:

- **Resets the ring buffer with `--reset`.** The `dumpsys gfxinfo` ring holds
  ~120 frames. Without an explicit reset it returns stale frames from whatever
  the app was doing earlier, or returns no PROFILEDATA block at all if the
  buffer drained. The script calls `dumpsys gfxinfo <pkg> reset` when
  invoked with `--reset`, then exits; the measurement run is a second
  invocation.

- **Derives the budget from the observed vsync period.** The period is the
  median gap between consecutive `IntendedVsync` timestamps in the framestats
  output. The script prints `inferredHz` alongside `vsyncPeriodMs` — this is
  the answer to the question "is the panel actually in its fast mode right
  now?" Use `--budget 8.33` to force the 120Hz gate explicitly if needed, but
  the derived period is the correct number for the Redmi.

- **Reports per window.** An RN `<Modal>` is its own window with its own
  refresh-rate vote. The script keeps each `Window: …` block separate so a
  Modal running at a different rate from the main window is visible as a
  distinct entry, not averaged in.

- **Gate:** ≥95% of frames must land within one vsync period; zero frames may
  exceed two periods (the "dropped frame" threshold). Exit code 1 on failure.

### Order of operations for a valid run

1. **Set "Motion smoothness = Adaptive" on the S22** (one-time; survives
   reboots).
2. Open the app; navigate to the surface under test and leave it idle.
3. `node scripts/framestats.mjs --reset` — zeros the buffer and prints a
   confirmation. This must happen immediately before driving the flow, not
   minutes before.
4. Drive the interaction: open the emoji panel, scroll the transcript, tap
   send — whatever the flow under test is. Keep it under ~four seconds so the
   ring does not wrap.
5. `node scripts/framestats.mjs` — reports per-window results and exits 0
   (pass) or 1 (fail). The `vsyncPeriodMs` and `inferredHz` lines are the
   first thing to check: if the S22 reports ~16.7ms / ~60Hz, stop, set
   Adaptive, and repeat from step 2.
6. For deeper attribution, capture with `scripts/perfetto-feel.sh` (VSYNC-app
   - FrameTimeline tracks) over the same interaction window and open the trace
     in the Perfetto UI.

## 2026-09-06 — W6 predictive back: deliberate non-adoption

**Pages read.**

- `developer.android.com/guide/navigation/custom-back/predictive-back-gesture`
  (overview + callback guidelines)

**What the docs require.**

To receive in-app gesture progress (the W6 animation), an app must:

1. Set `android:enableOnBackInvokedCallback="true"` in the manifest.
2. Register `OnBackAnimationCallback` (API 34+), which fires
   `onBackStarted()` / `onBackProgressed()` / `onBackInvoked()` /
   `onBackCancelled()` as the gesture unfolds.

The docs contain an explicit warning about the app's current pattern:

> "If your app was previously associating back logic with **conditional
> statements**, this might signify you are reacting to the back event after
> it has already **occurred**. **Avoid this pattern** with newer callbacks.
> If possible, move the callback outside of the conditional statement and
> instead associate the callback to an observable data holder type."

The doc's recommended pattern is: **register a callback when the UI state
that needs interception is active; unregister it when that state ends.**

**Why this app's back-guard contract is incompatible — for now.**

`App.tsx` holds a single `BackHandler.addEventListener('hardwareBackPress')`
subscription. Inside it, `consumeBack()` (from `src/lib/backGuard.ts`)
iterates a guard stack at the moment the event fires. When ChatScreen has a
live paid session its guard returns `true`, the confirm dialog appears, and
the pop is prevented.

That is precisely the "conditional at event time" pattern the docs warn
against. Adopting `OnBackAnimationCallback` without resolving it causes:

1. `onBackStarted()` fires → the W6 animation begins (chat screen starts to
   slide away).
2. `onBackInvoked()` fires → `consumeBack()` runs → the guard intercepts →
   a confirm dialog appears.
3. But the animation already played. The screen must visually snap back, then
   a dialog appears. That looks like a rendering bug, not a polish feature.

Preventing the animation from starting when a guard is active would require
synchronous Kotlin-side knowledge of JS guard state — either a native mirror
of `backGuardCount()` updated by `backGuard.ts`, or a per-guard
`OnBackPressedCallback` registered and unregistered as sessions open and close.
Both require refactoring `backGuard.ts` (and App.tsx's back handler) to the
doc's recommended "enable/disable by observable state" model.

**Decision (RULE 1 point 6 — stated departure).**

W6 is **not implemented**. No manifest change, no `PredictiveBackModule.kt`,
no `src/lib/predictiveBack.ts`. The existing `platform.test.ts` assertion
that `enableOnBackInvokedCallback="true"` is absent remains correct and must
not be deleted — its comment now records the pre-condition for W6 adoption.

**Pre-condition before W6 can be re-attempted:**

Refactor the back-guard system so that each guard registers an
`OnBackPressedCallback` (via a native bridge or via RN's own
`AndroidX OnBackPressedDispatcher`) for the duration of the state that needs
interception, instead of using a single always-on subscription with a
conditional. Once guards are expressed as registered/unregistered callbacks
rather than a conditional at event time, `OnBackAnimationCallback` can be
registered only when no guard is active and a route exists to pop — and the
animation will only ever start when the back will actually commit.

The `OnBackPressedCallback` note from the doc is the safety net either way:
`BackHandler` continues to fire through `onBackPressed` regardless of the
`enableOnBackInvokedCallback` flag, so the guard stack keeps working
correctly in the current state.

| `Gesture.Simultaneous` | `useSimultaneousGestures` |                                                                                                                                                                                                                                                       |
| `Gesture.Exclusive`    | `useExclusiveGestures`    |                                                                                                                                                                                                                                                       |

Firing conditions are otherwise unchanged: v3's `onDeactivate` runs only when
`oldState === State.ACTIVE`, exactly the guard legacy `onEnd` had — compare
`v3/hooks/callbacks/eventHandler.ts` with
`handlers/gestures/eventReceiver.ts`.

**The one structural change: `Turn.tsx` switches its discretes with `enabled`.**

The builder let the composition be assembled by a ternary chain
(`target !== null && onTap !== undefined ? Exclusive(longPress, tap) : ...`)
because `Gesture.LongPress()` was a plain constructor. `useLongPressGesture` is
a hook: it and `useTapGesture` run on every render whatever the props are, and
`useGesture` creates the native handler in an effect keyed only on the handler
tag — so selecting a subtree afterwards saves nothing and makes the composed
tree's SHAPE depend on props. Both are now declared unconditionally and gated
with `enabled`.

That is only equivalent because of an Android fact rather than a hope:
`GestureHandlerOrchestrator.recordViewHandlersForPointer` skips a handler when
`!handler.isEnabled` before it is ever added to the orchestrator's list, and
`hasOtherHandlerToWaitFor` only consults that list. So the disabled long press
of a still-uploading photo cannot strand the tap that waits for it in the
`Exclusive`. Asserted in `chatSurface.test.ts`.

**Coordinate space: unchanged, and it needed checking.** The v3 detector
inserts a native `RNGestureHandlerDetectorView` and attaches the handlers to
THAT view, not to the child — which would have moved the pinch focal point out
of the frame `MediaViewer`'s `onLayout` measures. It does not:
`GestureHandler.coordinateView` descends into the detector's single child, "the
same coordinate space V2 and the V3 VirtualGestureDetector report in", and the
detector is `display: 'contents'` so it takes no part in layout.

**New gate — `platform.test.ts` › "gesture callbacks are workletized".**

A gesture callback that is not workletized still works; it is dispatched to JS
instead, one round trip per frame. Nothing throws and nothing warns, and the
only symptom is a drag that lags the finger. RNGH 3 passes callbacks as
properties of a config object, and it is the `react-native-worklets` babel
plugin that adds the `'worklet'` directive: the hook names are listed in
`gestureHandlerObjectHooks`, argument 0 of each is registered as a workletizable
OBJECT, and `forEachWorkletizableObjectProperty` workletizes every
function-valued property of it (no allow-list of callback names, which is why
`onActivate`/`onUpdate`/`onDeactivate` are covered without the plugin knowing
those names). The gate compiles all four files through the project's real
`babel.config.js` and asserts every callback carries `__workletHash` and
`__closure` — 15 callbacks across the four files. It catches both a worklets
upgrade dropping a hook name AND a config the plugin cannot traverse (a spread,
a `useMemo`, a variable built elsewhere); both mutations were run and both fail
it.

**Dead citation found.** `Turn.tsx` cited
`docs/fundamentals/gesture-composition/` for the Exclusive wording. That URL is
a **404** — a citation that had gone dead survived every green build, and the
wording it carried ("Priority is decided through the order of gestures") is not
the wording on the page that governs today. `chatSurface.test.ts` now bans that
path alongside `docs/legacy-gestures/`.

## 2026-09-10 — Launch-verification remediation pass

Closing out the remaining gaps from the launch-verification pass. What was fixed
in code, and what is genuinely gated on a device / a deploy / infra and therefore
cannot be signed off from the repo.

### Fixed in this pass (code, verified in-repo)

- **Cold-open header flash.** `ChatScreen` asserted the literal "Conversation" as
  the title whenever `threads`/`providers` were still `undefined` — every cold
  open (launch, deep link) flashed that wrong word before the real name arrived.
  Now the fallback fires only once the sources have RESOLVED; while either is
  loading the title is blank (the bar reserves its height, so nothing shifts) and
  the name fades in the moment `peer_display_name` or the directory row lands.
  The header's layout-stability across presence states was already handled
  (`ChatScreen.tsx` reserves a constant bar height); this closes the last residual.

- **arm-only release bundles (build-speed / AAB-size lever).** `android:release`,
  `android:bundle`, `android:bundle:closed` and the `play-upload.sh` build hint now
  pass `-PreactNativeArchitectures=arm64-v8a,armeabi-v7a`. Real phones are all arm;
  x86/x86_64 are emulator/ChromeOS ABIs the India market does not use. Play splits
  the AAB per ABI, so DELIVERED download size is unchanged — the win is build time
  (two native ABIs instead of four) and AAB/upload size. DEBUG keeps all four via
  the `gradle.properties` default, so the x86_64 emulator still builds and runs.
  https://developer.android.com/guide/app-bundle
  NOTE: the resulting AAB has not been built+installed on a device in this pass;
  the config is release-scoped and reversible, but confirm ABIs on the next build
  (`aapt2 dump badging` / bundletool) before shipping.

- **JS bundle size-regression gate (§32).** New `scripts/size-gate.mjs`, wired into
  `npm run verify` after `bundle:android`. The native size is Agora-dominated and
  fixed; the one size vector a code change can move silently is the JS bundle. Gate
  ceiling 6.0 MB against the 2026-09-10 baseline of 5.26 MiB (~9% headroom).

### Device-gated — implemented finding, NOT closed (RULE 2)

- **FLAG_SECURE does not cover RN `Modal` windows.** `MainActivity` sets
  `FLAG_SECURE` on the activity window for the production `release` variant, which
  covers every in-tree screen. But the app renders `Modal` (React Native, separate
  Dialog window) in 8 components — `MediaViewer` (full-screen intimate photo/video),
  `Sheet` (all bottom sheets), `PaperMenu`, `Turn`, `SpotlightCard`, `HomeTour`,
  `ChatStartHint`, and one in `ChatScreen`. A Dialog has its OWN window and does not
  inherit the activity's flags, so a screenshot/recording over an open MediaViewer
  or Sheet is NOT blocked — exactly the sensitive content the flag exists to protect.
  Recommended fix: apply `FLAG_SECURE` to each sensitive modal's Dialog window (or
  render MediaViewer as an in-activity overlay rather than an RN `Modal`). Either way
  the ONLY valid verification is `adb screencap` returning black over an open modal —
  a screenshot-blocking feature cannot be unit-tested, and shipping it unverified is
  the Credential-Manager failure mode. Left for the device phase, which is out of
  scope for this pass by instruction.
